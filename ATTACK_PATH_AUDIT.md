# Attacker-path review

Reviewed 2026-09-21. This is a source and limited unauthenticated public-endpoint review, not an authenticated penetration test. `https://darsgah.vercel.app` currently serves an older build; repository fixes require deployment and migrations.

| Priority | Path and attacker action | Possible damage | Fix / verification |
| --- | --- | --- | --- |
| Critical | An authenticated school administrator could call Supabase directly and update `school_members.role`, `status`, or `custom_role_id`, bypassing the protections in `src/lib/services/settings.ts`. The old `members_update_principal_or_admin` RLS policy allowed the write. | Promotion to a protected school role, deactivation of other admins, or cross-school custom-role references. | `202609210003_member_privilege_guard.sql` adds a write trigger that rejects protected assignments, self-edits by administrators, identity changes, and foreign or privileged custom roles. Apply and test this migration before deployment. |
| High | An administrator could directly write `role_permissions` or `user_permission_overrides` using the public Supabase API despite the principal-only server action. | Grant broad access to school data and management functions. | The same migration revokes authenticated writes and removes the old administrator write policies; privileged writes go through authorized server actions with the service role. |
| High | A staff user allowed to insert a fee payment could bypass the application balance check by calling Supabase directly, or race two concurrent payments; `online_payment` could be recorded without provider verification. | Incorrect paid balances and forged receipts or financial records. | `202609210001_payment_integrity.sql` checks payment amounts against stored dues under a row lock for direct and app writes and rejects unverified `online_payment`. The form and schema no longer offer that method. Existing records need reconciliation. |
| Medium | A percentage discount over 100 was accepted by the validation schema; the database rejected the resulting negative payable only after the calculation. | Failed finance operations and inconsistent direct-write attempts. | Validation now caps percentage at 100; migration adds a database constraint. Fixed discounts are clamped to zero payable. |
| Medium | Contact-form spam protection used an in-memory map and a request header that could be spoofed outside trusted hosting. Branding uploads had no request limit. | Email spam or storage consumption across server instances. | Contact, upload, and application API routes now use the shared atomic limiter keyed by a HMAC of the trusted client address. Limits: contact 4/15 minutes, branding 10/hour, API 120/minute per IP. Apply `202609210002_abuse_rate_buckets.sql` after the original auth-rate migration. Hosting-level DDoS protection remains necessary. |
| Open | Student CNIC and birth date still authenticate parents; an already-issued staff JWT remains valid until expiry; hosted recovery-token expiry is unverified. | Personal-data exposure if identifiers or tokens are obtained. | See `CRITICAL_PATH_SECURITY_AUDIT.md`; these are release blockers. |

## Checks without a confirmed exploit

- All four Next.js API handlers check `getCurrentUser`; on the public deployment all four returned HTTP 401 without credentials. A malformed Supabase cookie also received 401. `/platform` and `/admin` redirected to sign-in. Expired-token and cross-user authenticated tests require controlled test accounts.
- ID-bearing app routes and services use the authenticated school ID or parent session student/school ID. The previous permission override IDOR was fixed. Direct Supabase access depends on deployed RLS; the member and permission-table bypasses above demonstrate why UI checks alone are insufficient.
- The local seed's `admin@scholarly.test` identity has a random generated password; no known default password was found. The seed must not run against production.
- No public signup, referral, promo-code, free-trial reset, payment checkout, or payment-provider webhook route exists. Platform subscription state is managed by platform-admin server actions and is not proof of payment-provider settlement.
- Text renders via React escaping; the contact email HTML escapes input. No `dangerouslySetInnerHTML` or direct user-controlled SQL execution was found. Search filter grammar and file content checks were tightened in the previous audit. This was not an exhaustive payload test of every authenticated form.
- Public requests to `/.env`, `/.git/config`, `/openapi.json`, `/swagger.json`, and `/health` returned 404. The live API responses did **not** include the repository's new CSP, `X-Frame-Options`, or `X-Content-Type-Options`; deploy and verify the header changes. HSTS was present at the hosting edge.

## Release verification

Apply migrations `202609200001` through `202609200003` and `202609210001` through `202609210003` in dependency order. Then test cross-school IDs with two controlled accounts; direct Supabase writes for administrator self-promotion, permission override, overpayment and online-payment methods; payment races; rate-limit 429 responses; expired/malformed sessions; and headers on the deployed build. Do not use real student or payment records for exploit tests.
