# Personal data flow audit

This inventory covers the application source and SQL migrations in this checkout. It describes code paths, not the live database, hosting access logs, backups, or third-party retention policies. Paths below are relative to this application directory.

## Collection and destinations

| Entry point | Data collected | Processing and storage | External destination or output |
| --- | --- | --- | --- |
| `src/app/(auth)/sign-in`, forgot/reset/change-password, staff creation in `src/lib/services/teachers.ts`, platform school creation | Email, password, name | Supabase Auth handles password verification and hashing; profile name/email and school membership go to `auth.users`, `public.profiles`, and `public.school_members`. The local SQL seed uses Blowfish `crypt` with a random password. | Supabase Auth. Passwords go to Auth APIs for verification or update; the app does not write them to a public table. Auth emails for reset are sent by the configured Supabase email provider. |
| `src/app/(auth)/parent-portal`, `src/lib/parent-portal.ts` | Student/guardian CNIC and student date of birth | Looks up `public.students`; a process-local keyed digest of CNIC is used for rate limiting. A signed session containing student and school IDs is placed in an httpOnly, SameSite=Lax cookie, Secure in production. | Supabase database. No separate password hash exists for this portal; CNIC plus date of birth is a weak knowledge check and should be replaced before treating it as strong authentication. |
| `src/app/(marketing)/contact/actions.ts` | Name, school, email, free-text message, selected plan; request IP for rate limiting | A process-local keyed digest of IP is held in a rate-limit map and stale entries are purged on later requests. Enquiry text is not saved in an application table. | Gmail SMTP receives name, school, email, message, and selected plan; the reply-to address is the sender's email. SMTP and the recipient mailbox retain the message under their own policies. |
| `src/components/profile/profile-form.tsx`, profile action/service | Name, work/personal email, phone, CNIC, gender, address, department, job title, emergency contact name and phone | Validated in the server action; saved to `public.profiles` and `public.school_members`. | Supabase database; own profile page and authorized staff directory. |
| Student form and spreadsheet import in `src/components/students`, student actions/service | Student and guardian names, CNIC, father CNIC/phone, email, phone, address, date of birth, admission and class data | Browser memory while editing/importing, then validated and saved to `students`, `guardians`, `student_guardians`, `enrollments` and related school tables. | Supabase database; authorized school pages, parent portal, CSV exports, and print views. |
| Parent portal details action | Student contact email, phone, address | Updates the matched student record after portal session validation. | Supabase database and authorized school/parent views. |
| Staff and teacher forms, transport forms, leave, attendance, marks, support queries, announcements and library actions | Staff names/contact/identity, driver contact and CNIC, leave reasons, attendance, grades, support text, notice text, library borrower names | Validated actions and services save to corresponding school-scoped Supabase tables; `activity_logs` also records actor IDs and some action metadata. | Supabase database; role-gated pages, realtime subscriptions and selected CSV/print views. Free-text fields can contain personal data supplied by users. |
| Finance and payroll forms | Fees, discounts, payment method, transaction/reference number, amounts, salary, deductions and remarks | Saved to `student_fee_accounts`, `fee_payments`, `finance_transactions`, `teacher_employment_details`, `salary_history`, `salary_adjustments`, `payroll` and related tables. The code does not collect card numbers or call a payment processor. | Supabase database; authorized finance/payroll views, reports, CSV, and print. |
| School profile branding upload | School logo and favicon image files | File bytes go through the server action to a Supabase Storage bucket; a public URL is saved for display. | Supabase Storage and its public asset URL. Do not upload photographs or personal documents as branding assets. |

No application use of `localStorage`, `sessionStorage`, or IndexedDB was found. React form state and file-import previews exist in browser memory. Browser/server Supabase clients use auth cookies; the browser client can access its cookies, so those auth cookies cannot be guaranteed `httpOnly` with the current client-side Auth and realtime design. The parent portal cookie explicitly has `httpOnly`, `sameSite: "lax"`, and production `secure` flags. Hosting, CDN, SMTP, and Supabase may record IP and device headers outside this repository; no application code persists a device fingerprint.

Student photo and staff avatar URLs can point to external image hosts. These hosts receive the viewer's IP when the browser loads an image. The image elements now suppress the page referrer, but an allowlist or first-party image proxy is still needed to prevent that outbound request entirely.

## Third parties and response boundaries

- **Supabase Auth/PostgREST/Realtime:** receives credentials, profile and school records, student/guardian records, operations, financial records and scoped realtime subscription identifiers. Service role use is server-side. The application relies on RLS and permission checks; deployed RLS state still needs a live check.
- **Gmail SMTP through Nodemailer:** receives only the contact form fields needed to deliver and reply to an enquiry. The source IP is used for in-memory rate limiting and is not placed in the email.
- **Other services:** no Stripe, analytics, error tracking, AI, Twilio, Firebase or AWS SDK call was found in `src`. The Supabase local config contains optional environment-based integration templates, which are not application calls.
- **Responses:** the four `src/app/api` routes require an authenticated user. Announcement API responses now use an explicit field list and omit school ID, author ID, audience targeting and raw joined rows. The notification API returns a defined summary. Server actions still return operational data to authorized clients; many services use `select("*")`, so a complete field-by-field minimization of every page and server action remains to be done. Record IDs used for updates are retained in client responses.

## Changes in this pass

- Removed email addresses, user IDs and fetched school objects from maintenance logs; removed raw error objects and messages from API handlers and many server action responses.
- Added a self-service profile deletion control requiring current-password verification. The `202609200001_account_profile_erasure.sql` migration makes database identity cleanup one transaction: it clears profile contact/identity fields, disables school memberships and platform access, clears identity-linked activity metadata and announcement reads, and clears a matching school contact. The action then replaces the Auth email and password, bans sign-in, and signs out. The database transaction and Auth update are separate operations, so an Auth failure still requires administrator follow-up. Opaque IDs and school operational/financial records remain to preserve referential integrity; free-text authored content and backups are not automatically erased. The migration and flow must be tested against a staged Supabase project before production use.
- Restricted announcement history by audience and changed unknown audience types to deny by default.

## Deployment follow-up

1. Replace parent portal CNIC/date-of-birth authentication with a dedicated secret or stronger identity method.
2. Move browser Auth operations behind server endpoints if `httpOnly` auth cookies are a requirement; the current Supabase browser client requires JavaScript-readable session cookies.
3. Review remaining broad database selects and each server action's serialized result against the consuming component, especially finance, payroll, student and library data.
4. Define retention and erasure rules for school records, free-text content, SMTP mailbox, platform backups and Supabase Auth identities. Test the deletion flow and verify that no direct or indirect identifier remains in the live environment.
